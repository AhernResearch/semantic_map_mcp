# 从模糊指令到导航目标：任务定义

2026-11-11。状态：第一轮任务整理与接口需求分析，不是已实现的Agent或已标注准确率基准。

## 1. 重新固定目标

用户请求最终应落到“对象/地点身份”和“导航站位”两个不同结果上。地图、图片和几何测量提供证据，不要求每次先画图。当前暂停改进topdown展示；已实现检索、图片读取和源记录管理保留。

核心循环：理解请求 → 候选召回 → 补充能区分候选的证据 → 确定指代或追问 → 解析并校验导航站位 → 返回候选/待确认/可交付状态。简单明确请求可以跳过图片或几何查询，不强制全流程。

任务集见 `../tasks/navigation_requests.json`。其中用户此前提到的表达仅表示需求来源，不表示这些指令在现场成功执行过。其他任务明确标为discussion_example或derived_test；没有录音、真实用户目标标注或现场实物确认，不称为真实用户测试集。

## 2. 用任务划分问题，而不是按地图种类划分

| 类别 | 示例 | 首要缺口 | 不应做的事 |
|---|---|---|---|
| 名称/类别 | 去会议室的柜子 | 范围与多个同类实例 | 见到top1就锁定 |
| 外观 | 去白色柜子那里 | 图像中颜色和对象身份 | 把CLIP分数当颜色证据 |
| 功能 | 找能打印东西的设备 | 外观、名称和实际功能 | 外观像打印机就断言可打印 |
| 参照关系 | 去门旁边的桌子 | 先确定是哪扇门，再取局部几何/图像 | 把所有门中最近的一扇偷偷当参照 |
| 视角方向 | 去我左前方的柜子 | 用户位置和朝向 | 把地图左上当用户左前方 |
| 路程偏好 | 去离我最近的柜子 | 起点、已绑定站位、可通行路径距离 | 对物体中心做欧氏距离排序后称最近可达 |
| 区域目标 | 去会议室 | 房间身份、入口或区域目标站位 | 强迫选择一个室内物体代替房间 |
| 会话指代 | 就第二个；不，是另一个 | 有序候选及会话版本 | 根据新一轮排序重解释“第二个” |
| 缺失/冲突 | 标签急救箱但图片像消防设施 | 图片核验和身份冲突 | 改标签或合并源记录来强行给答案 |
| 动态条件 | 找现在空着的椅子 | 新鲜观测及时间 | 用静态GS说明现在无人 |

## 3. 两层结果与一个交付条件

### 3.1 指代定位 GroundingDecision

- `status`：resolved / ambiguous / insufficient_evidence / needs_context / cancelled。
- `referents`：类型object或region、稳定ID、scene_id、snapshot_id。
- `candidate_ids`：尚存候选，不等于导航ID。
- `satisfied_constraints`、`unresolved_constraints`：分别附支持或反对的证据引用。
- `evidence_refs`：真实访问过的观测、源字段或测量；不引用未看过的图片。
- `question`：必要时一个能区分候选的简短问题。

resolved表示在给定语境和证据下指代已确定，不表示地图标签经过现场确认。ID明确的指令可以定位到记录，但对象是否与真实目标对应仍保留来源状态。

### 3.2 导航解析 NavigationResolution

- `status`：not_requested / not_attempted / blocked / ready。
- `referent`：明确绑定的对象或区域，而非任意最近候选。
- `goal`：有来源的registered_target_id或pose目标；没有就null。
- `binding_ref`：对象/区域与导航目标绑定记录、版本和审核依据。
- `navigation_map_id / navigation_frame_id`：目标所属地图与坐标系。
- `transform_ref`：需要跨坐标变换时提供经验证的变换及版本。
- `checks`：binding、coordinate、goal_validity、route（各项pass/unknown/fail及证据/时间）。
- `blocking_reasons`：如missing_binding、registration_unverified、pose_missing、route_unavailable。

不要求所有场景都先求路线才能返回一个已注册目标ID：必需检查由下游交付契约明确指定。但只要用户约束涉及“最近/可达”，就必须有对应路径证据才能宣称满足；未验证的路线不能默认pass。

### 3.3 交付状态

`handoff.status`：not_ready / awaiting_confirmation / ready / cancelled。`ready`要求指代已确定、导航解析ready、当前部署规定的会话确认已完成。即便ready，本研究模块也仅返回结果，不发送运动命令。

现有nav_target部署有同会话确认要求：status:"0"不是执行许可，status:"1"才可交由既有软件。新M-floor字符串ID不能直接塞进旧整数候选ID接口。未来适配层必须先有真实映射，不能强制转换或新造整数ID。

**M-floor当前所有导航目标都保留null**：本轮没有发现/建立其对象到导航站位的受核验绑定，也没有独立通过的机器人配准。对象指代分析可以继续，导航解析必须blocked或not_attempted。

## 4. 三个贯穿案例

### A. “去门旁边那个白色柜子”

1. 柜子类别与描述向量共同召回，保留多候选与来源；不把“白色”匹配直接当事实。
2. 查看候选代表图片，判断颜色、外形，并识别图像是否真正覆盖对象。
3. 召回相关门，确认请求中的参照；若图像或会话不足以确定参照，问“会议室门口还是走廊那一处？”——仅在当前候选确实提供这两种选项时这样问。
4. 对候选和参照取水平距离/框间距、区域来源、局部视图。程序输出数值与测量定义，模型解释“旁边”；隔墙/视线不明不能靠距离下结论。
5. 若两处仍符合，返回两者并问可区分属性。确定后另查绑定站位。

当前可做：柜子候选与图片读取。缺少：直接候选查询工具（现召回耦合绘图）、带证据引用的成对几何、独立审核答案、导航绑定。

### B. “去 S032 那张桌子那里”

这是派生接口测试，不是现场收集指令。源包存在S032（标签桌子、R01）。明确ID可定位到该记录，不需要先看图猜谁。

```json
{
  "grounding": {
    "status": "resolved",
    "referent": {"kind": "object", "id": "S032"},
    "basis": "用户明确给出当前快照内有效记录ID；不等于物理身份已审核"
  },
  "navigation": {
    "status": "blocked",
    "goal": null,
    "blocking_reasons": ["missing_verified_navigation_binding", "registration_unverified"]
  },
  "handoff": {"status": "not_ready"}
}
```

用户再次说“确认”也不能补出不存在的配准和站位。对象中心只用于定位展示。

### C. “去离我最近的柜子”

先明确“我”指用户还是机器人，二者不天然同位置。用户若想找最近可到达目标，需要起点位姿和候选导航站位的路径长度。无位姿时请求有效上下文；缺路线提供方时说明无法比较路线，不用直线距离静默替代。

当用户明确接受“只按地图直线距离”时，可以按该度量返回对象排序，但仍不能声称导航路径最短或已可达。

## 5. 真实数据锚点与答案审核

任务文件的`source_anchors`仅指可供查看的源记录，不是正确答案。自动生成的清单见`../tasks/mfloor_inventory.json`，记录scene.json SHA、snapshot以及记录ID、标签、区域、观测引用和已有产物。

当前可见例子：

- R01源登记为会议室；R03/R04都叫玻璃隔断区，因此区域名称也可能需要解歧义。
- S003标签急救箱，S108标签消防栓箱，位置接近；已有图片显示需要核验，不能仅凭接近合并或当两个真实设备。
- S032源框仅覆盖会议桌局部的疑点、S023投影落在桌面附近的疑点，都说明源几何不能直接充当实物真值。
- indoor-060与S009位置接近且都标摄像头：这是身份审核候选，不是自动同物规则。
- 现有源类型没有“打印机”不代表场景不存在打印机；对象视觉召回也不能覆盖完全未登记目标。

审核每个语义案例时填写：允许目标集合、等价实体组、决定性证据、不可判定条件、可接受的澄清与用户答复。用同一源标签生成问题再把该标签当正确答案不构成独立验证。可以先形成“GS可见证据答案”，现场身份真值另行核验。

## 6. 从任务反推最小工具能力

这是需求清单，不是立即上线的新API。现三工具继续可用，避免再次先造一套大接口。

| 能力 | 当前状态 | 下一步理由 |
|---|---|---|
| 场景/区域/类型发现 | list_scene已实现 | 可保留；明确目标不强制调用 |
| 直接召回候选，不画图 | Retriever已实现，公开结果耦合view_map | 优先抽出轻量search_candidates(queries, room_ids)；无需重写召回 |
| 对象图片和源字段 | inspect_objects已实现 | 保留，补足图片实际送到模型的日志 |
| 成对几何证据 | 对象已有框/中心，未提供成对测量契约 | 按任务需求提供距离/坐标/定义；不自动输出near真值 |
| 方向参照与新鲜度 | 未接当前机器人/用户状态 | 接有效位姿提供方；不预填默认朝向 |
| 导航站位解析与验证 | 新场景缺绑定 | 独立供应方，不归入对象召回分数 |
| 会话候选、改口、取消、确认 | nav_target有可借鉴逻辑 | 复用设计，不修改正在部署的服务 |
| topdown | 可选观察工具 | 仅布局有帮助时使用，不是必经入口 |

几何证据可包括object_center_xz_distance、bbox_gap、上下高度区间、各自坐标系和源框状态。墙体、遮挡、支撑关系没有证据就unknown。明确区分程序计算事实、模型解释和用户确认，不把任意模型猜测保存为地图事实。

### 如何比较路线是否有效

先审核任务答案，再进行同模型、同候选源和同图片预算的对照：

- A：候选列表+图片，固定一轮判断。
- B：候选驱动的按需工具循环，可获取图片、几何或追问。
- C：在B的同等预算中允许topdown，而非先强制画图。

独立报告：候选召回、指代选择、必要澄清、无证据断言、重复实体误计、导航交付条件违反、调用/图片/延迟成本。只有完成目标审核的子集才能计算语义成功率；当前未标注任务不能当测试已通过。所有M-floor任务当前导航blocked不能用来声称导航成功率，只能检验是否正确保留阻塞原因。

首轮审核顺序建议：明确ID与取消的协议案例 → 会议室同类对象消歧 → 外观与源标签冲突 → 参照/方向/路径缺失。审核前不继续调图、不重建地图、不改生产服务。
