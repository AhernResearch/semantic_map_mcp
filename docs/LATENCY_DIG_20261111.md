# 拼图任务耗时的逐轮诊断（2026-11-11）

本轮只做诊断，未修改主工具、prompt、每页5候选设置或在线服务。依据为前次真实trace、11条固定查询的本地CLIP检索，以及5次独立网关诊断请求。诊断代码与输出位于 `runs/latency-dig-20261111/`。

## 1. 拼图已消除了独立看图调用，剩余轮次全是检索

打印机：search ×3 → finish，共4次模型请求；白色柜子：search ×4 → finish，共5次模型请求。两例均没有调用inspect_objects或view_map。

因此不应继续把主要问题归因于“模型还在逐张调用图片”。当前要减少的是检索改写、翻页以及每次模型请求的等待。

## 2. 查询语言及多查询展示排序影响首屏

固定同一场景快照、ViT-H-14编码器与默认top10召回，单查询实测如下。S135只是历史模型曾选中的诊断对象，不是人工审核标准答案；表中排名不能解释为语义准确率。

| 查询 | S135在该次候选排序中的位置 |
|---|---:|
| 打印机 | 未进入该查询召回池 |
| 像打印机的设备 | 未进入该查询召回池 |
| printer | 7 |
| copier machine | 2 |
| printer copier large office machine with paper tray | 2 |
| office printer | 1 |

真实打印机trace中：首轮混合中文/英文查询后，S135位于第15；第二轮copier machine单查询已排第2，但合并后第7；第三轮英文长描述单查询第2，但合并后第6。三次都未进入5候选拼图。模型每次改写后都读第1页，没有读next_page。

当前跨查询展示规则为“最高单查询fusion_score降序，ID打破同分”。向量单通道的第一名均贡献1/(60+1)，第二名均1/(60+2)，因此不同查询中的高排名结果会相互竞争5个格子；该分值并不表达各查询的语义可靠程度。弱中文自由描述的高排名结果可挤走英文查询中的相关候选。简单累加多查询得分也未必解决，因为错误结果可能在多个相似中文查询中反复出现。

柜子实测：`白色柜子` 原样进入文本编码器，首屏为标识/绿植/门等，indoor-041与S016未入池；`柜子` 命中登记别名后实际编码 `cabinet`。`white cabinet` 可让S016排第1、indoor-041排第4；`a white storage cabinet` 分别第1、第2。这两个对象只是最终模型用于澄清的候选，不能因此认定真实目标就是其中之一。

本轮未增加翻译器或更换编码器。现有代码只对准确匹配登记类别名的查询使用英文别名，不会自动翻译“白色柜子”等自由描述。

## 3. 可以定位潜在多余的翻页，不能直接承诺反事实耗时

白色柜子最终澄清候选为indoor-041与S016：两者在第二张拼图中已经同时出现，随后模型又翻了第2、3页，最终没有把这些后续新增对象列为澄清候选。如果接受同样的澄清方式，存在更早提问的机会；这不证明后续对象都可无条件忽略。

打印机三张拼图共15个对象格，只有10个不同对象；最后一次改写得到的5格中有4个已看过。所有历史拼图还会随消息历史再次提交。

白色柜子5轮输入token数为2060、5789、9609、13373、17170；每轮仍是一张新拼图，历史中累计达到4张、20个不同对象。图片数量减少不等于累计上下文不再增长。网关usage的图像token细分为0，不能用其细分字段推算实际视觉token。

## 4. 同时段网关探针没有复现此前的长等待

使用相同明确配置的claude-sonnet-5-5和授权网关，凭据仅在进程内使用。前三次为流式探针，后两次使用相同输入和预算做非流式检查。没有执行模型返回的工具调用，无自动重试；诊断超时为连接10秒、读30秒。带图输入使用原trace中的一张真实拼图。

| 请求 | 流式总耗时 / 首内容 | 非流式总耗时 |
|---|---:|---:|
| 极短文本、无工具 | 2.24秒 / 2.14秒 | 未测 |
| 原任务首轮、无图、有工具 | 4.71秒 / 4.39秒 | 2.86秒 |
| 原任务后续、1张图、有工具 | 7.76秒 / 7.37秒 | 5.83秒 |

前三次TCP+TLS建立完成约0.24–0.29秒。前次真实任务无图首轮曾等待81.82秒；这次无图探针只需数秒，非流式也没有表现得比流式慢。因此既不能把81秒解释为图片引起，也不能认定改stream=True就会解决。

探针与上次任务不在同一时刻，不是重复随机对照；流式探针与非流式检查也各只执行一次。当前只支持“等待有明显时段/请求波动，长等待不是稳定的图片/连接固定成本”。网关排队、上游调度或模型内部处理的具体原因仍需服务端日志或请求ID关联，不能只凭客户端计时断定。

## 建议的下一步试验

保持每次1张拼图、5个候选不变，先只调整任务提示与工具说明：

1. 类别使用登记类别词，外观自由描述优先使用一个具体英文短语；避免同义中英混合查询挤占同一首屏。
2. 首屏没有匹配时，区分“翻现有候选池”与“改写查询”；不要连续改写后重复查看高度重合的首屏。
3. 已出现多个具体可匹配对象、确实需要用户区分时及时提出具体澄清，无须为同一个澄清问题机械翻完全部页。

这些策略不强制两轮结束，不降低证据要求。若该小试验仍漏首屏，再单独比较跨查询排序；不要同时调整拼图大小、候选数、模型和召回算法，以免无法归因。

证据：trace-audit.json、rank-audit.json、retrieval.json及query-*-tool.json、gateway.json与gateway-nonstream.json。所有运行证据均在Git忽略的runs目录，包含真实场景图片的请求按敏感数据保存。

后续已完成[固定候选与像素的图片组织对照](FIXED_PACKING_AB_20261111.md)：8次预定调用，打印机两种格式均选择S135，均值约9.48/9.32秒；白色柜子两组各一次输出截断，其余完整回答选择一致。没有证明拼图明显提速，且它不等同完整Agent端到端性能。
